## 一、我爸不下了

我爸今年六十多，退休之后最大的爱好是象棋。

去年我给他手机装了五个象棋 App，全是大厂或者高下载量的。我想着总有一个他能用。

结果过了两个月，我回家问他怎么不下了。他说了一句我没想到的话：

> 「〔待填：你爸的原话。真实的那一句，不要润色成"广告太多"这种总结。〕」

这句话把我之前的假设全推翻了。我一直以为适老化的核心是"看得清、点得准"——把字调大、把按钮调大，问题就解决了。但他这句话指向的不是视觉层面，是**心理层面**：他把每一次打开 App 都当成一次有风险的操作。

后来我把他手机里的五个 App 逐个打开看了一遍，大致是这么几类：

- 开屏 3 秒广告，跳过按钮在右上角，`×` 小到几乎点不中
- 要先手机号登录，登录完再弹"新人礼包"，关掉要点两次
- 把棋盘缩到屏幕下半部分，上半部分是"残局挑战"广告位
- 输棋之后弹「再来一局，看视频得金币」

不需要再分析了。**对一个不熟悉智能手机的人来说，一个界面里超过一半的面积在试图让他做别的事。**

他放弃的不是象棋，是"每次都要小心别点错"这件事的成本。

（先说明：我不是程序员，这是我的工作之外的业余项目。所以下面写的都是业余视角的取舍，不是架构师视角的最佳实践。）

## 二、真正的成本不是"学不会"

我后来把这个判断整理成了一个问题：**长辈用 App 的成本到底由什么构成？**

大部分人（包括之前的我）会答：学习成本。所以要「简化操作路径」「提供引导」。

但观察我爸用手机几次之后，我认为学习成本其实是很小的一块。原因是——**他只学一次，之后就是重复**。象棋规则他比我熟，点棋子、点目标位置这种交互，教一遍就会。

真正让他放弃的是另外两种成本，而且这两种是**每一局都要付**的：

**第一种：判断成本。** 屏幕上有多少个东西需要他决定"这个能不能点"？跳过的 `×` 在哪、这个红点是什么、"确定"和"取消"哪个是安全的。老年人对"误触造成后果"的恐惧是真实的——他们见过太多"点一下话费没了"的新闻。所以屏幕上每多一个可点元素，就多一次判断，就多一份风险感。

**第二种：失败感成本。** 这不是矫情。一个六十多岁的人，面对一个设计给二十岁人的界面，他感受到的是"这东西不是给我用的"。这种感觉会累积。他那句"怕点错"的潜台词其实是"我觉得我会搞坏它"。

这两种成本都是**每局重复支付**的。而学习成本是一次性的。

所以启发性结论是：

> 优化目标是让「重复支付的成本」趋近于零，而不是让「一次性成本」更低。

这跟我最初的想法完全相反。我原本打算做一个「新手引导」——三步教程，第一局高亮提示。后来我把这个方案删了。

因为**引导本身也是成本**。一个需要教程才能用的界面，等于承认了界面自己讲不清。

## 三、三条原则

最后落下来是三条，按重要性排序：

### 原则一：减（把东西删掉，而不是收起来）

「收起来」和「删掉」是两种完全不同的操作，很多人会把前者当成后者。

- 收起来 = 折叠、二级页面、长按出现。**判断成本还在**，因为他不知道那里有没有东西、要不要去点。
- 删掉 = 不存在。判断成本归零。

具体做了什么：

**首屏只有四个按钮**：和电脑下棋 / 挑战过去的自己 / 我的成绩 / 和家里人下。

四个，不能再多了。而且是四个大色块，不是图标配小字。

这里有个细节：原底座（这个项目是基于一个开源象棋项目改的）的首屏菜单是作为**棋盘上的遮罩层**出现的。技术上没毛病，但我改成了棋盘**下方**的独立面板。

原因是遮罩层有一个隐蔽的失败模式：点空白区域它就消失，直接露出棋盘——至于这局棋是什么时候开始的、谁先走，用户完全不知道。这个场景我没法只靠自己坐在这里想到，〔待填：你是怎么发现这个问题的——自己试出来的，还是看你爸操作时发现的？一两句就行〕

改成结构性分离之后，"菜单盖住棋盘"这个问题在**结构上就不存在了**，不是靠 z-index 打补丁。

**引擎技术数据默认全部折叠**。深度、节点数、NPS、耗时、评估分——这些是给懂棋的人看的，对我爸是纯粹的噪音。

但注意：我选择的是**折叠**而不是**删除**。因为我判断这类信息属于"我自己偶尔想看"，不属于"他需要看到"。所以保留了，但默认 `display: none`，入口是页面最底部一行小字「查看引擎数据」。

这就是"减"的边界：**减掉的是他的判断成本，不是我的调试能力。**

**删掉的东西清单**（这个更能说明问题）：

| 删掉的 | 为什么 |
|---|---|
| 开屏任何东西 | 没有任何理由存在 |
| 注册 / 登录 | 战绩存本地就够了，不需要账号 |
| 所有广告位 | 一个都不留 |
| 会员 / 内购入口 | — |
| 联网 | 断网能玩，反而更稳 |
| 新手引导 | 见上，引导本身是成本 |
| 音效开关 | 太细，不值得占一个决策 |
| 设置页 | 唯一需要设的是难度，放在选难度那一步 |

「设置页」这一条我想多说一句。很多适老化改造的思路是"给一个极简模式开关"——设置里加一个「长辈模式」，打开之后字变大。

我后来认为这是**偷懒的做法**。因为它的前提是"正常模式是默认的，长辈是特例"。它把一个"要不要进设置页、要不要找到这个开关、要不要理解开关含义"的决策链，塞给了一个最不擅长做决策链的人。

**适老化不该是一个开关，应该是默认。**

### 原则二：藏（术语不进眼睛）

这条是三条里最花时间的，第二章会专门讲。

核心判断：**一个词只要出现了，就需要被理解。不理解就会产生"我不懂"的感觉，这也是失败感成本。**

所以所有技术词汇一律不出现在主界面：

| 原来的 | 现在的 |
|---|---|
| 深度 18 / 2.3M nodes / NPS 480k | （全藏起来） |
| 评估分 -0.35 | （全藏起来） |
| `h2e2` | `炮二平五` |
| 红方胜！ | 这局你赢了！ |
| 难度：Level 4 | 难度：高级 |
| 连败 3 局，已调整为 Level 3 | 这档有点难，我给你调简单点（第 3 档）。 |

最后一条值得单独说。难度自适应这个功能，很多 App 都有，但实现方式是**静默调整**或者**弹一个系统提示**。

我选择**明确告诉他，并且用朋友说话的语气**。

```js
if (result.direction === 'up') {
  return '你最近赢得多，我给你调难一点点了（第 ' + result.level + ' 档）。';
}
return '这档有点难，我给你调简单点（第 ' + result.level + ' 档）。';
```

为什么？因为**静默变难 = 突然开始输 = 不知道为什么 = 失败感**。用户会以为是自己的问题。

而"我给你调简单点"这句话，把因果讲清楚了，同时传递了一个隐含信息：**输了不是你的错，是难度不对**。

这比"你很棒"式的鼓励有用得多。前者是解释，后者是敷衍。

### 原则三：不让人失败（设计上不给他出错的机会）

这条听起来抽象，但落地很具体。

**具体一：触控目标 60px，正文 20px。**

一般 App 的正文是 14px，按钮高度 40px 上下。我用 20px / 60px。

数字看起来只是"大一点"，但 60px 意味着**拇指的指腹范围完全落在按钮内**，不需要瞄准。这是消除"点偏"这个失败类型的第一层。

**具体二：点棋子 → 点目标，两步确认，不拖拽。**

拖拽是个对老年人很不友好的交互。要求持续按住、精确移动、松手定位。任何一个环节手抖都会失败。

改成两步点击之后，**每一步都可以反悔**：点了棋子发现点错了，再点一次取消；点了目标位置落下。

**具体三：悔棋不设次数限制。**

有些象棋 App 会限制悔棋次数（"每局限 3 次"），那是为了维护对局严肃性。我的目标用户不需要这个——他下一局棋不是比赛，是消遣。而**"不能悔棋了"这个提示，本身就是一次失败**。

所以现在是无限悔棋。这里有个实现细节值得一提：人机对战时悔棋要**连撤两步**（撤掉 AI 的应手 + 自己的那步），否则撤完还是轮到 AI，它会立刻把同一着再走一遍，用户体验上就是"悔棋按钮坏了"。

**具体四：终局不给"输"。**

这可能是最争议的一条。输棋时的结束语不是「红方胜」，是「这局电脑赢了」；赢棋时是「这局你赢了！」。

我特意把主语换掉了——不是「红方胜」「黑方负」，是「电脑赢了」。

**输给一个具体的对手，比输给一个抽象的判定要好接受。** 而且"电脑赢了"这个说法本身暗示了对手的实力，不是他的问题。

然后是复盘卡。这是整个项目里我自己最满意的部分。

## 四、最难的部分：把引擎的话翻译成人话

这一章是技术性的，但也是我认为整个项目里唯一有点"设计"成分的地方。

### 4.1 复盘卡长什么样

一局结束，点「看复盘」，出一张卡：

```
这盘有进步的地方

👍 这步走得不错   马七进六
第 12 步你走马七进六，这一步很到位。

👉 这步可以更好   你走：炮二平五
这步不算错，但有更好的走法。引擎觉得走炮五平四更合适。

💡 下一盘试试
下一盘留意一下第 23 步，那步走炮五平四会更好。
```

三条信息，顺序是**先夸后批**，且只讲一个错。

为什么只讲一个错？

因为复盘的价值密度是固定的，但**接受度是有限的**。给一个业余棋手一屏"你这里错了、那里也错了"，他的反应不是"我要改进"，是"我下得太差了"。

所以我的策略是：**一局只讲一个错，且必须讲一个对的。** 那个"对的"是维持他继续下的动力。

### 4.2 怎么找到"一个对的"和"一个最该改的"

原理不复杂：把这局棋从头"重走"一遍，每一步都问引擎「在这个局面下你会走哪」。

- 玩家走的 == 引擎首选的 → **做对的步**
- 玩家走的 != 引擎首选的 → 算分差损失（厘分）

然后：
- "做对的步"取**最靠后**的一步（离现在最近，印象最深）
- "最该改的步"取**损失最大**的一步，且必须超过阈值

阈值是分档的：

```js
var LOSS_THRESHOLD = { 1: 120, 2: 100, 3: 80, 4: 60, 5: 50, 6: 40 };
```

第 1 档（入门）要损失 120 厘分才算失误，第 6 档只要 40。

这一行数字背后是个我差点犯的错：第一版我用的是固定阈值 80。这个值放在第 3 档没问题，但**放到第 1 档，几乎每一步都会被标成失误**——因为低档引擎本身就觉得很多棋不好，它的"最佳着法"和人的直觉差得远。要是长辈第一局就看到满屏红字，他不会有第二次。

**阈值必须跟难度联动。** 这不是算法问题，是心理学问题：水平越低的人，越需要更宽松的评价标准，否则他永远在"被批评"。

### 4.3 三个改写实例

这是"翻译"真正的工作。引擎给的原始信息是这样的：

```
info depth 18 score cp -35 nodes 2345678 nps 480000 time 4888 pv h2e2 h9g7
```

对人话的翻译要过三层：**坐标 → 中文记谱 → 意图描述**。

**实例一：坐标转记谱**

引擎说 `h2e2`。这是 UCCI 坐标（第 h 列第 2 行 → 第 e 列第 2 行）。

要说成人话，是 `炮二平五`。

这个转换比看起来麻烦，因为象棋记谱有几条容易搞错的规则：

1. **同一列有两个同种棋子时，用「前/后」区分**——「前炮进二」而不是「炮二进二」。三个及以上还要用「中」。
2. **「进」后面跟的是步数，「平」「退」后面跟的是目标纵线**。`炮二平五` 里的"五"是目标列，`车一进三` 里的"三"是走几步。
3. **马、相、仕走斜线，「进」后面记的是目标纵线，不是步数**。

第三条是最容易写错的。我第一版就错了，测试里专门有一条守这个：

```js
// 校验：开局「炮二平五」= 底炮(col7,row7) → (col4,row7)
```

红黑双方的"前"方向还相反——红方向前进是 row 减小，黑方是 row 增大。这种细节都得处理。

**实例二：分差转意图**

引擎说 `score cp -35`（落后 35 厘分，约等于 0.35 个兵）。

不能说"-0.35"，也不能说"你落后 0.35 兵"——他不懂 0.35 个兵是什么概念。

要判断**这 35 厘分是怎么来的**。所以我给每一步记了几个特征：这步之后丢了什么子、这步本来能吃什么子、这步该将没将。

然后按类型生成不同的话：

```js
if (row.lostPiece) {
  text = '这步之后你的' + row.lostPiece + '就被吃了，'
       + '当时应该走' + bestName + '，那样就不会丢子。';
} else if (row.missedCapture) {
  text = '这里有个子能吃你没吃，先走' + bestName + '把这子收掉更划算。';
} else {
  text = '这步不算错，但有更好的走法。引擎觉得走' + bestName + '更合适。';
}
```

关键在于**「丢子」「能吃没吃」这些是具体的、可验证的物理事实**，而"评估分 -0.35"不是。老人能理解"我的马被吃了"，不能理解"我的局面评估下降了 0.35"。

**实例三：不说棋谚**

`describeMistake` 里有一句注释是我写给自己的：

```js
// 不用「双车错」「海底捞月」这类术语，要么不用，要么带一句解释。
```

「双车错」对懂棋的人是精确的，对不懂的人是零信息。而"两个车交替将军"是六岁以上能听懂的。

**术语不是专业性的体现，是沟通失败。**

## 五、技术上的两个坑

这一章给同行看，普通人可以跳过。但我觉得这两个坑值得写下来，因为它们是**我自己造成的产品事故**，不是普通 bug。

### 坑一：两个 Service Worker 互相顶掉

这个项目的后 3 档难度用的是 Pikafish（Stockfish 的中国象棋分支）编译成的 WebAssembly。它跑多线程需要 `SharedArrayBuffer`，而浏览器只在**跨源隔离（cross-origin isolated）**的环境下才允许用 `SharedArrayBuffer`。

跨源隔离的条件是响应头里同时有：

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

GitHub Pages 不能自定义响应头。所以标准解法是 `coi-serviceworker.js` —— 用 Service Worker 拦截请求，动态往响应里注入这两个头。

我照做了。然后我又自己写了一个 `sw.js` 做离线缓存。

**于是就有了两个 Service Worker。**

浏览器同一 scope 下只能有一个 active 的 Service Worker。后注册的会把先注册的顶掉。我的 `sw.js` 比 coi 晚 800ms 注册，所以：

- 第一次访问：coi 注入头 → 跨源隔离成立 → 引擎能跑
- 但 sw.js 顶掉了 coi → 下一次导航时没人注入头了
- 第二次访问：`crossOriginIsolated = false` → `SharedArrayBuffer` 不可用 → **4~6 档全部失效**

我当时写了个探测页实测，输出是这样的：

```
PROBE3: {"crossOriginIsolated": false, "hasSAB": false, "controller": "/sw.js"}
```

最坑的是症状：用户选第 4 档，界面提示"刷新重试"，但**刷新永远无效**——因为刷新之后还是没头。

我的错在于：**把"注入头"和"做缓存"当成两件独立的事，用了两个工具。** 但它们在浏览器眼里是同一件事——都是 Service Worker 拦截请求。

修法是把两者合并进同一个 `sw.js`：导航请求注入头，其他请求走缓存。

```js
if (req.mode === 'navigate') {
  event.respondWith(
    fetch(req).then(function (res) { return withIsolationHeaders(res); })
      .catch(function () { /* 离线时从缓存取，同样注入头 */ })
  );
  return;
}
```

顺带一个认知：**跨源隔离是文档级的，只对当前这次导航生效。** 不是设置一次就永久成立的，所以每次导航都必须重新注入。这一点如果不理解，就会写出"只注入首页"的错误实现。

### 坑二：每次升级让用户重下 49MB

Service Worker 升级时会 `activate`，习惯写法是清理旧缓存：

```js
caches.keys().then(function (keys) {
  keys.forEach(function (k) {
    if (k !== CACHE_NAME) caches.delete(k);   // ← 灾难
  });
});
```

问题是我有两个缓存空间：

| 缓存名 | 内容 |
|---|---|
| `xiangqi-elder-v3` | 页面外壳（HTML/CSS/JS，几百 KB） |
| `pikafish-nnue-v1` | 神经网络权重（**51,585,654 字节**） |

`if (k !== CACHE_NAME)` 这个判断会把 `pikafish-nnue-v1` 一起删掉。

结果就是：**我每改一次 CSS，用户就要重新下 49MB。**

对一个用流量、在手机上、可能网速还不好的长辈来说，这不只是体验差，是"这个 App 又坏了"。

修法是加前缀白名单——只删自己家的：

```js
if (k !== CACHE_NAME && k.indexOf('xiangqi-elder-') === 0) {
  return caches.delete(k);
}
```

我做了实测验证：手动伪造一个权重缓存，然后触发全新安装，确认 `nnueKept = true`，两个缓存并存。

这两条现在都有测试守着，写成了**防回归断言**：

```js
ok(/req\.mode\s*===\s*'navigate'/.test(swSrc) && /Cross-Origin-Opener-Policy/.test(swSrc),
   'SW 给导航响应注入 COOP/COEP（SharedArrayBuffer 前提）');
ok(/indexOf\('xiangqi-elder-'\)/.test(swSrc),
   'SW 只清理自己的旧缓存，不误删 NNUE 权重缓存');
```

现在这个项目一共 98 项测试（32 项记谱 + 66 项端到端），全部是这种"曾经踩过的坑"沉淀下来的。我吃过一次亏，就得让它不可能再吃第二次。

### 顺带说个难度设计的坑

Pikafish 源自 Stockfish，但它**没有** `Skill Level` / `UCI_Elo` / `UCI_LimitStrength` 这些弱化参数。也就是说引擎本身不会下弱棋。

所以后 3 档的"弱"是我自己造的：让引擎用 MultiPV 返回多个候选着法，再按 softmax 温度采样挑一个不是最优的。

```js
{ level: 4, depth: 10, movetimeMs: 3000, multipv: 3, temperature: 120 },
{ level: 5, depth: 12, movetimeMs: 5000, multipv: 1, temperature: 0 },
```

`temperature` 越大越"不理性"，0 就是全力。第 6 档没有深度限制，纯靠 5000ms 时间控制。

而前 3 档用的是另一个引擎——Wukong，纯 JS，只有 57KB，MIT 协议。它的弱法是更朴素的：限制搜索深度 + 按概率随机走一步明显差的棋。

```js
{ level: 1, depth: 1, blunder: 0.35 },  // 35% 概率走一步烂棋
{ level: 3, depth: 4, blunder: 0.06 },
```

双引擎的好处是：**前 3 档首屏加载 0 字节**。打开就能下，不用等 49MB。这也算一种"不让人失败"——等待 49MB 下载的过程中走掉的人，比下输一局走掉的人多得多。

## 六、还没做好的

这一节可能是全文最重要的。少数派读者大概最讨厌的是"我做了个东西，它很完美"。所以我把我知道的缺陷全列出来。

**1. 49MB 的权重仍然是负担。**

我知道有按需加载的方案（用户选到第 4 档才开始下），也评估过 Git LFS——但 GitHub Pages 不展开 LFS 指针，走不通。目前的妥协是"前 3 档零下载"，但选了高档还是得等。

对一个可能用 4G 流量的长辈，49MB 是个心理门槛。这个我还没解决。

**2. 复盘是模板式的，会重复。**

`review.js` 的函数名下面写着「模板版」。这是实话——它是规则拼句子，不是生成。同样类型的失误，第 5 局和第 15 局给的话一字不差。用得久了，用户一定会察觉"这话它上次说过"。

还有个小的啰嗦：复盘卡里"马七进六"这个着法名会出现两次（一次在标签右边，一次在正文句子里）。这是我拼接文案时没去重造成的，看久了会觉得机器味重。

真正的解法需要接入一个语言模型，但那意味着联网、意味着响应时间、意味着成本。对这个项目不划算。

**3. 「挑战过去的自己」曾经是个死按钮。**

这个必须单独写，因为它是我上线之后才发现的，而且是我自己写的。

首屏四个按钮里，「挑战过去的自己」的卖点是"用你三个月前的水平跟你下"。但它的点击回调是这样的：

```js
if (global.elderStartPastSelf) global.elderStartPastSelf();
else Elder.setStatus('还没有可以挑战的旧棋局');
```

`elderStartPastSelf` 这个全局函数**我从来没定义过**。所以这个 `if` 永远走 else 分支——无论你有没有历史棋局，点下去都只显示"还没有可以挑战的旧棋局"。

更难看的是它不报错、不崩、也不卡。它只是安静地什么都没做。这种 bug 靠"自己点一遍"是测不出来的——因为你点完看到一句"还没有旧棋局"，会以为是自己没下过棋。

修法是把实现补上（取时间最早的那一局，用它的档位和执子方开新局），并补 11 项断言守着，包括"用最早那一局而不是最近一局""明确告知是多久以前""没有旧棋局时不收起菜单"。

顺带发现第二个问题：提示语"在跟三个月前的你下（第 2 档）"我原本是同步设置的，结果被开局流程的状态更新（"正在准备引擎…"→"轮到黑方走子"）当场覆盖。**实测在真浏览器里才看出来**——jsdom 里没有 IndexedDB，这段代码根本跑不到。改成延后 900ms 再说。

这两个 bug 的共同教训：**测试通过不等于功能可用。** 98 项测试全绿的时候，那个按钮还是死的。

**4. 只有中文。**

我自己的能力限制——界面文案里有很多"这局你赢了""这步不算错，但有更好的走法"这种口语，翻译成英文就没了味道。要做英文版得重写而不是翻译，我没做。

**5. 记谱转换还有边角没覆盖。**

三个及以上同列棋子的「前/中/后」已经处理了，但极少数情况下（比如两个兵都在底线附近）我的排序可能和标准记谱有出入。当前测试覆盖了开局常见着法和几个特殊局面，不是全覆盖。

**6. 没有真机长期测试。**

我只在自己手机和我爸手机上测过（华为 Mate 50 Pro + 一台旧安卓）。iOS Safari 只做了基本验证，没做过长期使用测试。"添加到主屏幕"在 iOS 上的行为细节和安卓不完全一样，这块我不能说没问题。

**7. 微信内置浏览器用不了高档位。**

微信内置浏览器缺少多线程 WASM 环境，难度会自动降到 1~3 档。这个没法绕——技术上做不到，我只能选择"降级但能玩"而不是"报错"。

**8. 项目基于别人的开源底座。**

这个得说清楚。规则层、棋盘渲染、引擎桥接来自 [justa-cai/chess](https://github.com/justa-cai/chess)。我做的是**适老化改造**：主题层、行为层、记谱转换、复盘引擎。这不是从零开始的原创项目，我也不想把它包装成原创。

因为用了 Pikafish（GPL-3.0），编译成 WASM 后随项目分发，整个项目必须是 GPL-3.0。这也是为什么它开源。

## 七、结果

先说清楚：**我不知道这东西对别人家有没有用。**

我自己能确认的只有一件事：它现在做的事，跟他之前放弃那五个 App 的理由正好是对着的——没有开屏、不用登录、不用怕点错、输了还有话说。

〔待填：这一段是全篇最有说服力的地方，但只能由你来写。建议包含三件事——
① 你爸现在真实的使用频率（"每天一两局"还是"一周看一次"，照实写，哪怕很少）；
② 他具体说过的一句话（关于复盘、关于难度、关于某个按钮）；
③ 有没有哪个设计被他无视了，或者用成了你完全没想到的样子。
如果暂时还没有真实反馈，就把这段改成「刚给他装上一周，还不知道」，然后写你打算观察什么。**不要编。**〕

至于「挑战过去的自己」这个功能，我想说说它的设计意图，因为这个机制我觉得挺有意思：

历史战绩存进 IndexedDB 的时候，我顺带存了当时的难度档位和执子方。所以可以做到"调出三个月前你的档位，跟你下"——不是跟一个固定难度的电脑下，是跟一个**具体的、过去的你**下。

心理机制在于：**跟电脑下棋的对手是抽象的，跟自己下棋的对手是具体的。** 而"我比三个月前的我强"这个结论，是任何鼓励文案都给不了的。

当然，这个功能在我写这段文字的前十分钟才刚刚修好（见第六节第 3 条）。所以它到底有没有这个效果，我也还没验证过。

我现在的态度是：设计逻辑说得通，但**说得通不等于有用**。等他用一段时间再说。

## 八、如果你也想做一个

最后给三条我认为最值得的：

**一、先观察，别先设计。**

我最初的方案文档里写满了"新手引导""极简模式开关""一键求助"。这些都是我坐在这里想出来的。

真正的转折点是那句"我怕点错"。**用户的真实成本，往往不是你想的那个成本。** 而这个只能靠观察，不能靠访谈——问"你觉得这个 App 有什么问题"是问不出来的，没人会说"我心理压力大"。

**二、把"减少"当成主要工作量。**

我这个项目的代码量分布大概是：适老化主题层 19KB，行为层 24KB，记谱转换 7.7KB，复盘引擎 8.4KB。

但真正花时间的不是写这些，是**决定删掉什么**。删掉设置页、删掉新手引导、删掉悔棋次数限制、删掉音效开关——每一个删掉的决定都比写一个新功能更难，因为它们看起来都是"有用的小功能"。

**给长辈做东西，"有用"是个陷阱。** 有用的东西加起来就是负担。

**三、让失败变得不像失败。**

这一条是全部里最有效的一条。无限悔棋、先夸后批的复盘、把"红方负"改成"电脑赢了"、难度自动降档并且解释原因——这些都是同一个思路的不同实现：

> 降低"我做错了"的发生频率，以及在它无法避免时，改变它的叙述方式。

我爸不怕输棋。他下了一辈子棋，输赢是常态。

他怕的是被一个不懂他的东西评判。
