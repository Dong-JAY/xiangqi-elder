0. 结论先行

项目结论
推荐形态网页版（做成 PWA，可"添加到主屏幕"当 App 用）
技术底座fork justa-cai/chess（纯前端象棋 AI，六档难度，双引擎，GPL-3.0）
我们自己写的增量① 战绩持久化 ② 复盘反馈引擎 ③ 适老化 UI 改造

不推荐微信小程序（合规死结）｜ 独立 APK（老人装不动 + 要重装更新）

什么情况下应该改成 APK： 如果你爸不会/不愿用手机浏览器打开链接（非浏览器场景），或者你打算把这个软件给很多人装，那就换 APK。技术上 APK 是网页版的薄壳，一周内可从同一份代码包出来。

1. 需求还原

你提的四条硬需求 + 一条隐含需求：

#需求拆解
1没有广告✅ 全部自研实现，无第三方广告 SDK，天然满足
2记录战绩局级记录（日期/难度/执子/结果/手数）+ 统计（胜率/连胜/当前档位）+ 导出分享
3难度提升⚠️ 不该让老人手动选 6 档。应该做成自动升降档（连胜升、连败降）+ 手动锁定兜底
4复盘反馈引擎重走整局 → 定位关键失误步 → 用中文说人话（"这步该炮五进七"）
5隐含：给爸爸用这才是真正的设计主线。见 §4.1
需求 3 的重新定义：参考项目是"6 档手动选"，但对 60+ 老人，"我该选第几档"是个认知负担。正确的做法是系统按他的表现自动调——连赢 3 局升档、连输 2 局降档，并在升档时用一句话告诉他"你最近赢得多，给你加难度了"。手动选择保留在设置里作为兜底。

2. 三种形态的可行性裁决（全部实测，非推测）

2.1 微信小程序 —— ❌ 不推荐，两个独立的阻断点

阻断点实测/查证结论
SharedArrayBuffer 不可用微信小程序沙箱无法下发 COOP/COEP 响应头，微信也未开放该配置入口 → SharedArrayBuffer is not defined → Pikafish 多线程 WASM 直接跑不起来。依据：CSDN 技术问答 + libpag 官方微信构建指南（明确写"微信运行时不支持 SharedArrayBuffer，因此必须单独构建单线程 WASM"）
棋牌类目要版号微信小游戏审核指引：棋牌类目需额外提交《网络游戏出版物号核发单》《产品合规报告》《产品运营报告》。个人主体无法申请棋牌类目。走普通小程序账号虽可注册，但一个完整对弈游戏被判定为棋牌类目、被要求补版号的概率很高
包体积主包 ≤2MB、总包 ≤20MB。49MB 的 NNUE 权重进不了包（需运行时下载落到小程序文件系统，链路更脆）
平台工具链不支持WorkBuddy sites 技能明确拒绝发布小程序（预检直接报错），只能回微信开发者工具手工上传审核发布

2.2 独立 APK —— ⚠️ 可行，但性价比低

维度评估
技术可行性✅ WebView 壳加载同一份网页代码，跨源隔离可用 androidx.webkit 处理
本机工具链❌ 当前完全没有：JDK 未装、Android SDK 未装、Gradle 未装、ANDROID_HOME 未设。需下载 JDK 186MB + cmdline-tools 153MB + platform/build-tools（国内镜像可达但要配 proxy）
分发门槛⚠️ 给老人装 APK 要开"允许未知来源"，每次更新还要重装一遍
应用市场要软著 + 备案，个人走完全流程周期长

2.3 网页版 —— ✅ 推荐

维度评估
技术可行性✅ 纯静态，零构建，服务器零成本
国内可达性✅ 本机实测：justa-cai.github.io 连测 3 次，总耗时 0.68s / 0.87s / 1.03s，wukong.js（58KB）与 NNUE 权重（206 分片响应）全部 200
老人上手✅ 微信里点链接 → 浏览器打开 → "添加到主屏幕" → 桌面有图标，以后一点就开（只需做一次）
更新✅ 改完刷新即生效，不用让老人重装
无广告✅ 自己写的，没有广告位
战绩存储✅ IndexedDB 本地存，零成本零依赖

3. 参考项目拆解：我们白拿什么，自己写什么

底座选 justa-cai/chess（GitHub，GPL-3.0，2026-09 仍活跃）。它已经是一个跑通的纯前端象棋 AI，我完整读了源码，结论如下。

3.1 直接白拿（不重写）

能力位置说明
完整规则引擎js/xiangqi.js白脸将、自杀着、蹩马腿、塞象眼、炮翻山、九宫限制，终局判定（无子可走即判负）
双引擎桥接js/engines/bridge.jsWorker 型 WASM 引擎与同线程 JS 引擎收敛成同一套异步接口
低档引擎js/engines/wukong/纯 JS，57KB，零下载，MIT 许可
高档引擎js/worker/pikafish-engine.wasmPikafish（C++→WASM）+ NNUE 权重，GPL-3.0
六档难度表js/difficulty.js已实测标定：档 1-3 用 Wukong 靠"随机失误率"调弱（加深度不涨棋，是实测结论），档 4-6 用 Pikafish 的 MultiPV + softmax 温度采样调弱
跨源隔离补丁coi-serviceworker.js给 GitHub Pages 补 COOP/COEP 头，绕过"静态托管无法自定义响应头"的限制
缓存策略三层查找内存 → Cache Storage → 网络，49MB 权重只下一次
难度调参是这块底座最有价值的部分。原作者已做过机机对战标定（L3:L4 = 0:18 等），我们直接继承，省掉最耗时的调参环节。

3.2 必须我们自己写的（这是真正的增量）

#模块难度说明
A适老化 UI 改造★★★见 §4.1。原 UI 是深色科技风面板 + 小字 + 侧栏，对老人不友好；且原项目明确写着"移动端未实测"
B战绩持久化 + 统计★★IndexedDB 存局记录，胜率/连胜/当前档位统计，导出为图片或文本
C复盘反馈引擎★★★见 §4.4。需要新写 UCCI→中文记谱的转换（原项目没有这个函数，我 grep 确认过）
D自动升降档★★基于战绩表现驱动难度
E中文着法显示★★原项目侧栏显示的是 h2e2 这种坐标，必须换成"炮二平五"

3.3 ⚠️ 许可证提醒（重要，别踩坑）

  • Pikafish 是 GPL-3.0，编译成 WASM 后随项目分发，传染性覆盖整个前端产物。
  • 只给爸爸自用 → 不构成"分发"→ GPL 义务不触发，完全没问题。
  • 但如果你以后想公开发布这个软件（挂应用市场、分享给朋友群），必须开源整个项目。这个决定要在动手前想清楚。
  • 另有一个坑：底座仓库的 NNUE 权重是 51MB 的二进制文件。如果做 APK，包体会到 55MB+（微信/应用商店对小程序和 APK 都有体积限制，但 APK 无硬限制）。

4. 推荐方案详细设计

4.1 适老化改造（第一优先级，这是"给爸爸用"的落点）

原项目是给开发者看的，我们要做给老人用：

维度原项目我们改成
布局桌面横屏，600px 棋盘 + 560px 侧栏竖屏单列：棋盘占满屏幕宽度，引擎数据折叠进"详情"页
配色深色科技面板（#20242b）浅色高对比，字号 ≥ 20px，按钮 ≥ 56px 高
主操作多层嵌套菜单（开始→模式→先手）首屏两个大按钮：「和电脑下」「看我的战绩」。先手默认随机或上次选择，不问他
术语深度/节点/NPS/UCCI 评估分全部隐藏进"高级信息"。主界面只说人话：「电脑想了 2 秒」「这步走得不错」
落子反馈提示点保留，并加触觉+音效确认；可选"允许悔棋"开关
着法显示h2e2炮二平五
失败处理弹窗弹窗用大字，措辞口语化，不出现"GG"

移动端是最大的未知数（原项目自己标注了"移动端未实测"），风险点是 pikafish-engine.js 里的硬编码假设。这必须列为 P1 阶段的实测项——在你爸的真机上跑一轮，而不是模拟器。

4.3 战绩记录

存什么（每局一行）：日期时间、难度档、执红/黑、结果（胜/负/和）、总手数、每手着法（FEN 序列，用于复盘）、时长。

怎么呈现：

  • 「我的战绩」页：总胜率、当前连胜/连败、当前档位、近 20 局战绩条形图
  • 「复盘」入口：从最近一局进复盘，或从历史列表选任一局
  • 导出：一键生成一张战绩卡片图片（可直接微信发给家人），或导出文本

存哪：IndexedDB（本地）。不联网上传——老人的棋谱没有分享价值，隐私上也不该外传。这也意味着换手机会丢战绩，这是个取舍；如果后面要做多设备同步再上云服务。

4.4 复盘反馈引擎（最有价值，也最需要设计）

原理：对局结束后，让引擎把整局"重走"一遍，逐步比较你实际走的 vs 引擎认为最优的，用分差损失（厘分）定位关键失误。

引擎已经能输出 score cp / score mate 和 MultiPV 候选着法，数据是齐的。我们需要新写的：

  1. UCCI → 中文记谱转换器（底座没有）：h2e2 → 炮二平五。象棋记谱有"炮二平五""马8进7"的特殊写法（同一列多个子用"前/后"），要按标准规则实现。
  2. 损失计算器：每步对比 top-1 与实际走法后的评估分，差值超阈值即标记为失误。阈值要按档位分别标定（低档位不该报太多失误，否则老人一看全是红字就放弃了）。
  3. 关键节点识别：吃子、将军、漏防、被将军未应——这些是老人最容易犯且最值得讲的错误。
  4. 人话点评生成：用模板库 + 规则填充。例如：
第 23 步（你走：马8进7）
引擎推荐：炮5进7（可绝杀）
这步之后你的马被白车吃掉，白方下一手将军就赢了。

为什么不上 LLM 生成点评：技术上可以（平台有免密 LLM 调用），但每次复盘都要联网 + 有 token 成本 + 结果不稳定。建议先做模板版（离线、免费、稳定、可预期），跑顺了再考虑把 LLM 作为可选增强。

复盘是"慢思考"场景——爸爸下完一局愿意花几分钟看，这正是学棋的关键窗口。别做成要点的按钮，要做成他愿意主动打开的"看点"。

4.5 部署与分发

项方案
托管GitHub Pages（底座作者已用 coi-serviceworker.js 解决跨源隔离，且我实测国内可达）。备选：WorkBuddy sites 部署单端口 Python 服务（自加 COOP/COEP 头）
分发把链接发给爸爸（微信直接发）。首次引导：微信打开 → 右上角菜单 →「在浏览器中打开」→「添加到主屏幕」
更新改完推送即生效
关键提示在系统浏览器（Chrome/夸克/小米自带浏览器）里打开可启用全部 6 档；在微信内置浏览器里打开，Pikafish 多线程可能不可用 → 自动降级到 Wukong JS 引擎的 1-3 档（底座双引擎架构天然支持，这是刚需不是过度设计）
建议在"添加到主屏幕"的引导页里明确写一句："记得用浏览器打开，不要在微信里直接玩，否则电脑水平会低一些。"

5. 实施阶段

阶段内容验收标准风险
P0 地基fork 底座 → 本地跑通 → 部署 GitHub Pages6 档难度均可玩，PC 端无 console 报错低
P1 适老化（最重要）竖屏布局、大字号、人话文案、中文着法、成绩页在爸爸的真机上完整走完一局，字看得清、点得准中（移动端未实测）
P2 战绩IndexedDB 存储 + 统计页 + 导出关掉浏览器重开，战绩还在低
P3 复盘记谱转换 + 损失计算 + 点评生成复盘能准确指出"这步该走什么"，人话读得懂中高（需反复标定阈值）
P4 自动难度连胜升档 / 连败降档 + 提示连续 3 胜自动升档，提示文案友好低
P5 打磨音效、触觉、对比度、无障碍老人独立使用 1 周无求助低

建议节奏：P0+P1 先做出来给爸爸试用 3-5 天，收集他的真实反馈（哪里点不动、看不清、听不懂），再决定 P3 复盘的具体形态。不要一口气做完所有功能再给他——适老化只能靠真实用户迭代出来。

6. 需要你拍板的 5 件事

  1. 形态：网页版（PWA）先行，还是你决定直接上 APK？
  2. 能不能公开发布：只给爸爸自用（GPL 无义务），还是想开源/上架（须整个项目开源）？
  3. 战绩要不要跨设备：本地存最简单；跨设备要引入账号体系 + 云服务（成本和复杂度上一个台阶）
  4. 复盘点评要不要上 AI：模板版（离线免费）还是接 LLM（更聪明但联网 + 有成本）
  5. 部署位置：GitHub Pages（省事，实测可达）vs WorkBuddy sites（平台内托管，更可控）
